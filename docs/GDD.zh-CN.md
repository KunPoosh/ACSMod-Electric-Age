## 1. 已确定方向

- 独立 Acbric Java MOD：电气时代 / Electric Age。
- 建立有实际数量与收支约束的电力：发电机提供输出，蓄电池提供储能，用电设备具有额定功率。
- 保留原版内容与行为，在其基础上增加独立的新模块和机制；不把原版设备自动改成电气设备。
- 电网全船共享，无布线。船体断裂后各部分独立供电，没有发电或储电模块的部分失去供电；有电池的部分仅能在剩余电量及可用放电功率范围内供电。
- 继续复用原生攻击能力，同时设计首个新增攻击形态“链式闪电”：首击按原版方式选定攻击点，命中后从命中点衍生子闪电，随机攻击附近模块；使用原版爆炸伤害结算。扩散规则已按后续章节实现，验证范围见 TESTING。
- 探索哪些通用能力适合成为 Acbric 公共接口；电力玩法与框架职责分开。
- 当前已实现电力、过载、闪电与模块持久化；原版设备保留原有行为。完整战役与联机仍待验证。

## 2. 已确认的设备定位与玩家体验

核心体验：通过设计发电、储能与负载组合，在持续作战能力、短时爆发、空间、重量、造价及受损韧性之间作选择。

用户确认电气系统属于高风险、高收益路线，集中供能与更强设备性能是其主要价值：

- 电力在全船电网中直接分配，末端电气设备无需等待人员逐份搬运煤炭供能，减少对燃料搬运人员、路径和响应时间的依赖。燃煤发电机仍依赖原版煤炭配送；减少的是末端燃料搬运，不代表所有人员需求归零，也不改变原版设备。
- 发电与储能承担共同供能责任。供电设施受损可能使多个系统同时降频或停机；浮力、推进及武器能力下降可能进一步放大战损，形成全舰灾难风险。这是已定供电、战损和原生物理机制可能产生的结果，不新增脚本式强制连锁爆炸或额外全舰伤害。
- 使用弹药的电气武器继续依赖原版人员搬运弹药；电力系统不统一取消武器弹药或人员条件。闪电武器默认不消耗弹药，但保留装填周期，属于本轮明确的无弹药设备类型；不因此推导为无需操作人员。电气武器主要以更强的额定性能体现额外用电及供能设施成本的收益，过载在此基础上进一步提升。
- 单个新武器的基础参数可按定位设计；这不更改已定功率倍率映射：首版降频/过载影响装填速度和射速，不自动让单发伤害、弹速或精度随功率变化。具体性能优势、重量、造价及人员数值另定。
- 平衡评估看整船的发电、储能、武器、人员与后勤投入，兼顾电力中断时的脆弱性；不通过削弱原版设备强迫玩家使用电气设备。

循环提案：设计供需 → 战斗观察收支 → 应对发电机或电池受损 → 战后调整设计。

首版六类设备已确定，见第 4 节。具体时代设定、科技树和剩余设备数值待讨论；基础美术方向已确认；不自动采用 ProjEOL 的设定或素材。

## 3. 已确认的运行与操控规则

### 发电、储能与持续负载

电池定位已确认：用于短时爆发及供电中断后的应急，不以支撑数分钟独立作战为默认目标。平衡上应避免常规电池配置覆盖大多数短战斗、使发电机失去价值。具体容量和应急秒数按参考舰船负载讨论，见 [数值总表](BALANCE.zh-CN.md)；首版供需绝对数值及参考负载推导时间现已确认，统一见数值总表。此定位不新增电池寿命倒计时、强制安装发电机或禁止堆叠的机制。

- 发电设施支持消耗原版煤炭或不消耗资源两种方式，由模块定义决定；不增加新燃料资源。煤炭配送复用原版机制，无燃料类型不检查煤炭供给。
- 满足原生人员、燃料等工作条件时提供模块定义的额定输出，无法工作时为零。首版不额外按 HP 比例降额；工作时空载也按原版节奏耗煤，不按负载节煤。具体人员及输出数值另定。
- 电池自动充放电，不要求玩家手动切换。发电不足时主动补足模块额定运行需求，剩余电量和最大放电功率共同约束可提供的供电。
- 电池可辅助足额复机及过载，沿用“常规供电 → 足额复机 → 均匀过载”的分配顺序。发电与电池合计仍不足时，才按已确定的降频/离线规则结算。
- 发电在满足当前负载后有剩余时给电池充电；不能把同一份输出同时算作设备用电和充电，也不能把电池自身放电当作新增发电量循环充电。电池分别定义容量、最大充电及放电功率，首版效率均为 100%；初始电量及补给延续规则见下文，具体容量及功率数值另定。
- 电气武器只要处于电气在线状态，就持续请求额定功率，无目标、等待装填或停火不会切换低功耗待机。缺电时实际耗电等于分配功率，离线后不继续消耗；过载时按过载分配规则增加需求。额定是正常需求，并不是缺电后仍能强行扣除的固定电量。
- 武器暂不按单次攻击额外扣电，不新增待机功率和充能攻击机制。电力消耗不自动改变原生弹药规则，具体武器内容另定。动力设备仅无移动命令时仍维持在线需求；降落造成的实际停用则关机，见下节。

### 动力待命与降落停用

用户确认没有移动命令时维持此前在线耗电规则，同时要求降落停用的对应模块关机。区分普通待命与原生操作造成的停用：

- 普通待命：动力模块仍具备工作资格且电气在线，就继续请求额定功率；过载请求开启且实际获得超额功率时，照常增益及自损。
- 降落停用：受影响的电气浮力/飞行推进模块从负载与过载分配集合移除，耗电为零，不产生过载自损，也不输出电气增强后的升力/推力。只处理对应设备，不因降落关闭全船武器、发电机或储能；原版设备行为保留。
- 停用不撤销组过载请求。再次恢复工作后，根据原请求与可用供电决定是否实际过载。用户已确认统一复机：重新起飞时先恢复原生工作意图及人员资格，再按额定功率门槛复机；缺人、损坏、缺电等恢复场景采用同一门槛，不能形成缺电不派人、没人不通电的循环。

本地 1.2.15.2 静态依据：CommandButtonsPanel.groundShip（约 808 行）发送 ground 命令，Combat 的 ground 执行器（2312 行）调用 Airship.groundShip。Airship.groundShip（1910 行）设置下降目标与 grounding；grounded（1948 行）另检查近期地面接触与目标高度，并不等于按钮刚被按下。Airship.tick（2951–2964 行）在 grounded 状态限制飞行推进，并设 suspendiumRunning = !grounded；Module.running（537 行）读取推进/浮力运行标志。Module.staffJobPriority（2361 行起）将对应岗位优先级降至 0.001，而非立即删除岗位或强制全员离岗，StaffJob.active（约 2658 行）仍有自身条件。

适配建议：跟随实际着陆停用阶段，下降途中保留原版所需能力，不在点击降落按钮时直接切断全部升力。不以速度为零、无移动命令或单独 enginesRunning=false 作为电气关机依据；后者普通待命时也可能出现。地面载具的行走动力不能因接地而误关机；复合职能模块需另核对适配。电气关机状态不能反过来永久阻断人员恢复和起飞请求。以上为静态接入研究，未验证实机降落/起飞或新增跨版本钩子。

### 模块功率与启停

模块定义额定功率 P_rated、最低运行功率 P_min、过载功率 P_overload。能否过载是独立资格，不要求所有模块都支持。非过载模块的第三个值如何表示，待接口设计确定。

- 正常工作以额定功率为目标。
- 运行中的设备在分配功率低于额定但高于最低功率时降频；低于最低功率时关机。
- 因缺电关机后，必须重新分配到额定功率才能启动，形成不同的启动/停止门槛。
- 用户已确认恰好等于最低功率时可继续运行，即 `P_min <= P < P_rated` 为降频运行；严格低于 P_min 才关机。任何原因停机后，恢复原生工作资格的模块都须取得完整额定功率才能复机。
- 首版降频按实际功率与额定功率之比缩放下述工作能力，具体映射已确认。

### 首版性能映射与未来工具模式

对仍处于运行状态的模块，降频能力倍率为 `m = P_actual / P_rated`。最低功率决定是否能运行，不把最低到额定区间重新归一化为 0–100% 能力。低于最低功率时仍按既定规则离线。

| 设备 | 功率影响的能力 | 首版不随功率改变 |
| --- | --- | --- |
| 电气武器 | 装填速度、射速 | 单发伤害、弹速、精度 |
| 电气推进装置 | 推力 | 重量、结构属性 |
| 电气浮力装置 | 升力 | 重量、结构属性 |

例如分配到额定的 60%，且足以保持在线，则以正常装填速度/推力/升力的 60% 工作。对于装填和射击间隔，倍率作用于工作速度：时间按原时长除以 m 换算；具体原生路径需避免同一个速度加成被重复施加。m=0 时按离线处理，不进行除法。

过载沿用连续、平滑且适度奖励完整过载的曲线，各模块定义自己的最大能力提升幅度；作用目标与上表一致。曲线系数与首版增益已确认并记录于 [数值总表](BALANCE.zh-CN.md)，尚待实机平衡验证。

用户提出未来可能扩展工具模式。当前仅记录该扩展方向，未定义模式内容、切换规则或接口，不作为首版必需功能，也不改动当前供电、启停及过载规则。后续可为工具定义对应的能力映射，不必将所有工具效果硬套为武器射速。

### 常规缺电：等比例供电、逐个离线与余量复机

用户确定：在线模块按额定功率等比例获得供电，最低功率占额定功率比例较高者自然先离线；离线模块退出工作负载分配，不持续分走一份不足以启动的电力。只有在线模块的额定需求已满足，且存在足够的额定功率余量时，才给关机模块分配重启电力。

令可用于常规负载的有效供电为 S，在线模块集合为 A；对正额定功率的用电模块，`r = min(1, S / sum(P_rated_i, i in A))`，`P_i = r × P_rated_i`。每个模块的最低运行比例为 `t_i = P_min_i / P_rated_i`。零额定功率模块不参与此除法；发电机、储能及原生工作资格另行处理。

结算顺序：

1. 按当前在线集合计算共同供电比例 r。
2. 如果有模块低于自己的最低功率，优先移除最低比例 t_i 最高的模块；若最低比例相同，则按内部优先级决定断电次序。
3. 每移除一个模块，立即更新在线额定总需求和 r；其释放的供电重新分配，直到剩余在线模块均达到最低条件。不能一次关闭所有按旧 r 判断不达标的模块。
4. 在线额定需求全部满足后，计算 `R = max(0, S - sum(P_rated_online))`。仅在 R 足够支付某关机模块的完整额定功率时复机，并立即扣减 R，再处理下一台。

内部优先级在断电与复机中反向使用：高保留优先级者后断、先启。默认额定功率较小者具有较高保留优先级，先获得复机电力；完全相同时用稳定身份打破平局，具体身份键留给接口设计。断电阶段最低比例始终是第一条件，内部顺序只处理同阈值情况，不会变成过载优先级。本轮用户认可该启停设计。

突发大幅供电下降时，以上逻辑可以在同一个模拟步连续移除多台模块，不为了显示逐个熄灭而让实际缺电设备多工作几帧。供电缓慢下降时会自然表现为逐台离线。优先级和求解中间状态不得在 UI 中反过来修改供电。

示例（仅说明规则）：A 额定/最低为 100/80 kW，B 为 200/100，C 为 100/30。总额定 400，供电降至 280 时 r=70%，A 首先离线。剩余额定 300，重新分配后 B≈186.7、C≈93.3 kW，均可继续工作。供电恢复到 350 时，B/C 已额定运行，但余量只有 50，A 仍关闭；达到 400 时才足以重启 A。

由此产生有意的恢复迟滞：一组设备在降频状态可能能共同运行，但完全关闭后不一定能在同样供电下全部启动。小额定设备先复机可能使大模块长期等待；若供电持续不足以在维持在线设备额定运行的同时启动大模块，这不是调度遗漏，而是所选规则的结果。用户已认可先保留此取舍，不加入抢占、等待加权或手动优先级机制。

### 船级过载命令

- 新增“武器过载”和“动力过载”按钮；分别影响全船可过载武器，以及可过载的动力/浮力装置。
- 过载按钮接入原版指令系统，以原版舰船指令消耗限制切换，取代此前的独立锁定时间/冷却方案。过载是持续模式，不因一段独立计时结束而自动关闭。
- 过载请求把设备的目标功率上限提高到 P_overload。
- 统一采用均匀过载，取消按模块内部优先级依次过载的方案。部分过载有实际收益，增益曲线较平滑；完整过载保留适度奖励，不产生悬殊的门槛落差。首版曲线与增幅已确认，统一见 [数值总表](BALANCE.zh-CN.md)。
- 组模式与供电结果应分开表达：开启过载不保证每台设备已得到过载功率；指令就绪也不能绕过缺电停机规则。缺电不自动取消过载请求，供电恢复后按该请求重新计算实际效果。
- 两按钮同时开启时共用冗余电力，所有参与模块采用相同过载完成比例，无组间优先级；断裂继承、俘获清除过载请求已确定，不增加新的过载计时器。

### 原版指令复用与切换细节

已核对本地 1.2.15.2 反编译快照：`Airship.readyForCommand()` 检查指令点是否足够、指挥能力及麻痹等限制；`commandGiven()` 清空本船指令点；`commandPointsGenerated()` 依赖工作的指挥模块及人员，需求由 `commandPointsRequired()` 计算。`CommandButtonsPanel` 的已有操作通过 `Combat.giveCommand()` 发送，`Combat.execCommand()` 按命令类型分派至公开的 `EXECS` 表。原版资源会再生，并非整场战斗仅能消费一次的道具。

复用方向、双向消耗指令及多选/无效操作规则已确认；尚未实现：

- 用户已确认开启和关闭均消耗一次原版指令，不采用免费关闭方案；重复设置当前状态或不适用的操作不扣指令点。
- 新增独立命令类型，不挪用原版射击模式/专注命令，也不让过载自动改变它们。
- 命令携带明确目标状态（开启/关闭），而不是到执行时才取反；执行时重新检查就绪、目标舰船和适用条件，实际变更时调用原版指令消耗。
- 两组过载与需要就绪的原版命令共享本船指令恢复过程，不为两个按钮各做一份冷却。恢复后可以切换另一组，也可以执行其他原版操作。
- 仅改变过载模式请求；资源分配在既定模拟阶段处理。通过命令执行路径变更，不在绘制回调直接改状态。
- 开关均消耗指令，因此指令未恢复或指挥设施失效时可能无法手动退出过载；设备仍可因缺电停机。该风险随用户本轮选择保留，不自动提供紧急免费关闭。

此静态核对不等于新增命令已具备联机/回放兼容性；还需验证命令路由、多人选择、状态保存和恢复，不能仅因调用 giveCommand 就宣称支持。

#### 多选与无效操作（已确认）

保留两个切换按钮，不增加第三个常驻指令。用户已确认以下行为：

### 过载自损（规则与首版数值已确认）

用户确认：只有实际过载的模块才持续受到基于模块最大 HP 的伤害，直接作用于模块而非外部装甲。按每模拟秒损失最大 HP 的固定比例描述；首版伤害率已确认，统一见 [数值总表](BALANCE.zh-CN.md)；尚未实现或实测平衡。

- 计算提案：`damage = H_max × k × dt_seconds`，k 是每模拟秒损失比例，不按当前剩余 HP 计算，也不按画面帧数扣血。H_max 采用已确认的模块实例有效最大 HP；与原生加成及上限变化的关系需验证。
- 自损率及对应算例见 [数值总表](BALANCE.zh-CN.md)。不受维修和其他伤害影响时，不同血量设备损失相同的耐久比例。
- 生效条件已确认：对应组的过载请求开启、模块具有过载资格且在线、实际分配功率高于额定时，才产生过载自损。额定运行、降频或离线时均不产生新的过载自损；已有损伤不会因退出过载恢复，其他原生伤害照常处理。
- 若伤害率固定、不随过载完成比例变化，部分过载与满过载每秒损失相同比例的 HP，因此满过载每单位耐久的收益更高。这会进一步鼓励充足供电，也可能削弱低比例过载的吸引力；需要连同增益曲线验证，不自动增加热量系统或改为功率比例伤害。
- 过载指令是持续目标状态，用户已确认缺电不会清除请求。分配遵守“常规供电 → 足额复机 → 均匀过载”，模块在可用余量内接近该目标，不抢占常规负载或复机功率。部分过载也算实际过载，无需等到完整过载才生效或受损；供电不足时回到额定、降频或离线，随后供电恢复便自动重新尝试过载，无需再次下令或额外消费指令。只有撤销请求才停止这种自动尝试；断裂继承、俘获清除请求，见战损规则。
- 用户已确认保留原生维修抵消自损。充足维修可能支持长时间过载，代价转为维修资源与人员占用；不能仅因存在自损就保证无法持续过载。
- 用户已确认允许自损扣至零并进入原生损坏流程，不保留最低 1 HP，也不加低血量自动退出。了解原版机制后，用户确认保留低血量殉爆：自损进入危险血量也可能自行殉爆，见下节。实时界面按下文简化方案处理，不要求常驻显示模块自损速率。

静态依据：本地 1.2.15.2 反编译快照的 `Module.doDamage(int)` 直接扣模块 hp，或在 holdOn 状态下扣 holdOnHp，不经过外部装甲；模块 tick 另有跨越零 HP 的损坏处理，REPAIR 分支会恢复模块 HP。实现宜沿用该损伤入口与正常更新时序，而不是直接写 hp。由于入口接收整数，小数伤害需确定性累计，不能每步截断导致小血量模块免伤。暂停、倍速、存读档及 holdOn 行为需专门验证；这些源码事实不构成新机制的运行验收。

### 原生起火与低血量殉爆：保留规则已确认

用户在了解殉爆是持续低血量检查后，明确选择不修改该机制：模块保留易燃易爆属性，允许过载自损使其进入危险血量并自行殉爆。此前的伤害来源隔离方案不再采用；不增加未修复过载磨损账本、专用风险血量或维修来源分摊。

本轮静态发现（本地 1.2.15.2 反编译快照）：

- `Module.java:281` 的 doDamage 仅扣 hp/holdOnHp，没有点火或殉爆随机判定。
- `Tile.java:240–255` 的 splashHit、`:444–459` 的 hit 在扣血之后另做低血量起火判定。直接调用 doDamage 可避开这两条命中点火路径；外部命中仍读取实际 HP，因此过载磨损可能使后续攻击更容易满足起火血量门槛。蔓延及已燃烧状态继续按原版处理。
- `Module.java:984–1005` 在 tick 内依据当前 HP、爆炸阈值、时间步和风险修正抽取殉爆引信；不要求本步刚受伤，也不记录伤害来源。低于阈值且 HP 大于零的可爆模块，即使不再扣血也可能启动引信。这里的危险并不是 doDamage 的调用次数直接叠加爆炸判定。
- 引信启动后独立倒计时；不因过载或关闭过载而清除既有引信、火焰或跳过模块 tick。关闭过载只停止后续自损，已有低血量风险仍在；维修与引信的交互沿用原版，不额外承诺修好就能取消已启动的引信。

实现方向：按模拟时间经 doDamage 对模块直接施加自损，绕过装甲，不主动调用命中点火判定；后续起火传播、外部命中及低血量殉爆保持原版。无需更改共享 ModuleType 属性或替换殉爆 HP 计算。小数伤害累计和 holdOn 等正常兼容处理仍需实现及验证。

已有研究的 method-comparison.json 记录 Module.tick 在 1.2.15.2 / 1.2.15.3 / 1.2.14 的方法字节码一致；本轮没有新增 Tile 跨版本核验或实际运行测试。后续需验证纯自损至零、混合伤害、停过载后继续低血量、维修顺序、既有火焰/引信、蔓延，以及模拟随机序列与保存恢复。

### 均匀过载（共池分配与曲线已确认）

武器、动力与浮力采用同一种均匀过载原则，不提供内部过载优先级或依次填满的规则。

用户已确认“均匀”为各参与设备具有相同的过载完成比例，而不是增加相同瓦数。令每个设备的额外功率需求 `D_i = P_overload_i - P_rated_i > 0`，可用于该分配池的冗余功率为 S，则：

`u = clamp(S / sum(D_i), 0, 1)`；`P_i = P_rated_i + u × D_i`。

此公式前提是参与设备的额定运行预算已满足；不把降频、关机或不具备原生工作资格的设备误当作已额定运行。没有参与设备时不做除法。超过满过载需求的余量不强行消耗，是否用于充电由储能规则决定。两按钮同时开启时，将所有参与设备纳入同一分配池以保持同一 u；关闭一组会释放其额外需求，另一组可能得到更高完成比例。

示例：设备 A 的额定/过载功率为 100/150 kW，B 为 200/300 kW；冗余为 75 kW 时，u=50%，分别分配 125 和 250 kW。两者进度相同，额外用电量按各自需求分配。

已确认连续增益曲线，形式为 `倍率 = 1 + B_max × (a × u + b × u²)`。B_max 及 a/b 的权威值见 [数值总表](BALANCE.zh-CN.md)。线性部分保证中间档有明显收益，小幅上弯使接近完整过载时稍有额外回报，无须在 100% 处突然加一档奖励。

曲线算例见 [数值总表](BALANCE.zh-CN.md)。倍率作用于已确定的装填/射击速度、推力及升力；射速倍率应映射为装填时间的倒数关系，不能把所有时间字段直接乘该倍率。

常规供电及余量复机采用上节确定的规则。阶段顺序确认为“常规供电 → 足额复机 → 均匀过载”，避免过载一直占用余量而阻止离线设备恢复。均匀过载无内部优先级；常规断电平局及复机顺序使用内部优先级。电池按本节供给侧规则自动补足供电，有剩余发电时充电。

启动分配必须真实预留额定功率，不能多台设备同时把同一份空闲电力当作启动许可。启停门槛能抑制最低功率附近的抖动，但不能替代稳定的分配策略。原生工作资格、供电启停和过载请求应分开维护；缺电、缺人、损坏及降落停用后恢复工作资格，统一采用足额复机门槛，复机后再按余量过载。原生人员调度与电气供电不得互相等待而使恢复永久阻塞。

- 整船设计统计采用类似原版陆行舰重量统计的紧凑行布局。电力一行显示“额定用电 / 发电功率”，前者包含全船电气设备的额定需求，后者只计发电输出，不将电池放电算成发电。

- 三种满过载需求合并为同一统计项，固定顺序为“武器 / 动力 / 全舰”，明确显示顺序标签。每个值都是该模式下的整船总需求，不能只显示该组自身需求或额外增量。动力包含推进与浮力；全舰表示两个过载按钮同时开启且对应设备均达到完整过载，其余设备仍额定运行。
- 令 N 为全船额定需求，W/D 为对应组的可过载设备集合，则武器需求为 `N + sum(P_overload - P_rated, W)`，动力需求为 `N + sum(P_overload - P_rated, D)`，全舰需求为 `N + sum(P_overload - P_rated, W union D)`，并集中的每个模块只计算一次。不能直接相加前两个整船需求，否则会重复计入额定负载；若两组无交集，等价于武器需求 + 动力需求 - N。
- 示例：额定需求 200，武器额外需求 60，动力额外需求 40，则显示“满过载需求（武器/动力/全舰） 260 / 240 / 300”。数值仅说明布局与计算，不是平衡参数。实际运行仍遵守共池分配；满过载需求是目标需求，不保证供电足以实现。
- 模块建造说明列出最低/额定/过载功率；发电机显示输出，电池显示容量与充放电上限。可过载模块列出满过载增益和自损率。详细数值放在设计阶段，不恢复战斗中的逐模块原因面板。
- 括号中的支撑时间建议默认采用全船额定运行、两个过载都关闭的工况，并明确标为“额定约 X 秒”。假设设备完好、人员和燃料满足、满电且负载固定。发电不足额定需求时，电池补足的是二者差额；在放电能力持续足够的简化条件下，时间为可用电量除以功率缺口。多种电池须考虑各自电量耗尽后放电能力下降，不将总电量除法直接当作保证时间。
- 续航边界文案为建议：发电足够时括注“额定无需放电”，不写无限总续航；电池输出不足以补足时括注“无法维持额定”，不伪报正常支撑时间。功率与能量单位、具体格式仍待定。整船不展示最大放电数字，但估算必须遵守该约束。
- 欠电设计仅提示，不禁止保存或使用。玩家可以主动选择电池爆发、部分设备降频或分阶段恢复的舰船；不自动改装或增加发电机。

#### 统一能量派生与伤害（规则及 1:1 基础映射已确认）

用户已认可“能量决定传播预算，分支参数决定形态”，并要求能量同时影响爆炸伤害。保留最大子节点数 B；B=1 为串联，B>1 允许分叉，能量不足或邻近候选少时自然退化为单支或结束。

- 武器定义初始攻击能量 E0，作为该攻击的权威参数；每次主闪电从 E0 开始，子节点持有分到的剩余能量 E。已确认先根据该节点命中前的 E 推导标称爆炸伤害，按原版护甲/伤害流程结算，再扣除正值命中损耗 C 后派生。子闪电不能复制父节点的完整剩余能量；基础换算系数已定为 1，设备具体数值尚未确定。
- 最简版本在剩余能量 R=E-C 非负时，取 `k=min(B, 合法候选数, floor(R/C))`，从候选中随机选择 k 个不同模块，将 R 分配给这些子闪电，默认均分；各子节点继续同样过程。k=0 时结束，未用预算不自动退回舰船电池。余数分配需要稳定规则，不能因浮点取整创建额外能量。
- 示例仅说明机制：E0=100、C=20，首击后剩 80；最多两个子节点时各获 40，各命中后剩 20，可再各衍生一个节点；完整路径最多命中 5 次。B=1 时同样预算可形成最多 5 个节点的单链。目标不足或预算无法组成下一次命中时，实际命中数可以更少。
- 已确认能量到基础 blast 伤害按 1:1 换算。整数伤害入口可采用 `D(E)=floor(E)`，最终取整细节待接入核对。面板从同一 E0 映射得到 D(E0)，表示“首击爆炸伤害”，不手工维护另一份独立且可能失配的固定伤害值；实际加成/取整需与结算路径一致且避免重复施加。原版伤害修正的接入尚待验证。
- 例：E0=100、C=20、alpha=1、每节点最多两支，完整树的节点标称伤害为 100 → 40/40 → 20/20，面板显示首击 100。若改为单链，伤害序列为 100、80、60、40、20。这些仅为规则例子，不是武器定值。
- 固定初始能量只保证相同属性条件下首击标称伤害固定，不保证整链累计伤害相同。上述分叉示例累计 220，串联累计 300，均为护甲等处理前数值；候选数量、路径、护甲与提前终止还会改变实际结果。传播预算不复制并不等于累计伤害与 E0 一比一守恒，应按整次攻击及不同布局评估平衡。已确认不增加距离损耗或额外分叉成本。
- 攻击能量是单次闪电的强度与传播预算，不自动新增持久化资源，也不改变“武器在线持续耗电、子闪电不额外扣电”的现有规则。若要从电网或电池逐发支付 E0，则须另行修改供电与开火契约，不能默认获得授权。过载首版仍只改变射速/装填，不自动增加 E0 或首击伤害。
- 正值成本使节点数量受能量约束，仍保留明确的总节点数/层数运行保护，并使用有界迭代派生而非无限递归。根与所有分支共用去重集合；目标选择和预算分配顺序需稳定，避免先执行的分支顺序随帧率变化。

按用户允许处理具体细节及推进开发准备的指示，先以面向单人自定义战斗的可玩测试包为目标，包含全部六种设备、电网/电池/启停、两个过载指令、甲板线圈塔链式攻击、电力条与建造统计。用原版全科技环境测试，不把等待科技研究作为玩法验证前置条件。正式战役解锁仍采用已确认的机械加工方案。

按以下顺序验证，每阶段只记录真实完成的结果：

1. 核心规则：供需与电量收支、欠电逐个停机、足额重启、统一过载、伤害小数累积和闪电预算。以确定输入验证边界，避免只观察正常满电情况。
2. 单机实战：正常供电、断煤、发电机受损、电池耗尽、降落/起飞、船体断裂、维修、过载混合多选，以及闪电孤立/密集/装甲/跨舰目标。包含相应战斗保存恢复与已有原版设备对照。
3. 战役：科技建造资格、连续未补给两战的电量延续、实际补给充满、存读档及自动结算保持原版规则。
4. 联机：双端相同命令下电量、启停、过载损伤和闪电目标/伤害一致；覆盖约定模式的保存恢复。具体模式以验收结果界定，不因双方安装相同 JAR 默认通过。

战役与联机保留在既定设计中；状态可保存与模拟确定性从实现起就要考虑，不能后续再拼接。首个测试包先做单机可玩验收，不等于删除后续模式目标，也不等于正式发布支持范围已经决定。六设备素材已静态检查通过；用户已允许 UI 暂时复用，首轮运行时引用原版图标，专用图标不作前置条件。开发准备与具体里程碑见 [实施顺序](IMPLEMENTATION_PLAN.zh-CN.md)。目前尚未实现玩法、安装、提交或发布。

## 6. 技术约束与验收方向

- 按模拟时间结算；暂停、倍速和回放不得由现实时间驱动充电。
- 总收支守恒。不能把负电量截断后仍让所有设备正常运行。
- 缺电不冻结着火、爆炸、水淹等原生更新。
- 修复、断裂、复制与恢复不会重复创建储能。
- 验证补给后满电、无补给连续两战的剩余电量延续、战斗/战役保存恢复以及战后状态回写；不能因重建战斗对象或加载存档而重新充满。补给规则已确定不等于战役存储已实现；自动结算不增加专项机制。
- 区分过载请求与实际供电；检查原版指令消耗/就绪、重复及失效指令、阈值、额定功率重启及公平分配，不允许重复扣指令或重复承诺同一份功率。
- 缺电逐个移除后重新分配，避免过量关机；核对同阈值断电与反向复机顺序、突发供电损失、长期缺额及初始全关闭状态。无冗余时可检查供需变化，但不向关机模块预分配电力。
- 不在 UI 绘制中推进资源，不让每个负载重新扫描全船。
- 自动结算完全沿用原版，不新增专项算法；电量延续及联机同步仍需分别验证，不因战斗功能可用而默认完成。
- 不预先承诺某个游戏版本、帧率或联机模式已兼容。

建议里程碑：M0 工程骨架 → M1 确定 GDD → M2 隔离电力核心 → M3 最小可玩内容与存储 → M4 按约定扩展模式与内容。M0 骨架与 M1 设计基线已具备，开发准备已完成，M2 起尚未实现。
