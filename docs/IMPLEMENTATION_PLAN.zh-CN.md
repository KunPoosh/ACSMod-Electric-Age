## 交付目标

先完成单人自定义战斗中的六种设备、电网、电池、启停、过载与闪电攻击，用全科技环境测试。战役和联机保留在设计目标中，保存格式和确定性从第一阶段考虑，按后续阶段分别验收。日常实现细节由开发处理，改变既定玩法时再讨论。

以下为实施时采用的分期。dev.2 已形成阶段 1–4 的单机测试包；阶段 5 的对象存储/补给入口已接入，全战役闭环与阶段 6 尚待验证。没有自动安装、提交或发布。

## 实施顺序与完成条件

| 阶段 | 内容 | 完成条件 |
| --- | --- | --- |
| 1 电力核心 | 定义、实例状态、按船调度、充放电、欠电逐个停机、足额重启、统一过载、损伤小数累积 | 无游戏依赖的边界测试验证能量收支、分配顺序、临界电量耗尽、暂停与步长处理；相同输入重复产生相同结果 |
| 2 最小实战闭环 | 配套资源打包，先接发电机、电池和推进器；煤炭/人员资格、输出缩放、运行状态贴图 | 隔离实例中能建造并运行；断煤后由电池接替、耗尽后降频/停机、恢复后足额启动；同场原版模块行为不变 |
| 3 六设备与过载 | 浮力、电气火炮、两个原版指令通路的过载切换、自损、降落、断裂、俘获与维修 | 验证实际过载才自损、命令只扣一次、请求与实际状态分离、拆分不复制电量；先复用 UI 图标 |
| 4 闪电与界面 | 表面目标、共享访问集合、能量派生、原版单点爆炸伤害、程序电弧、电力条与建造摘要 | 一次模拟结算整次攻击，视觉不影响命中；孤立/分叉/装甲/跨舰目标符合规则，完成六设备单机可玩包 |
| 5 战役与恢复 | 机械加工资格、战斗/战役序列化、连续战斗、实际补给、自动结算数据保留 | 无补给不免费充电、补给充满、保存恢复不丢状态；自动结算算法保持原版 |
| 6 联机验证 | 原版命令驱动、稳定遍历及随机调用、双端状态比较与恢复 | 以实际验证模式声明支持，不能以相同 JAR 或大厅握手通过代替模拟一致性验证 |

状态保存先在阶段 1 定义格式与身份契约，阶段 2 起验证对象重建与战斗恢复；阶段 5 是完整战役闭环，不是首次考虑存储。

## 代码边界

- `definition`：设备规格和数值读取，数值权威仍为 BALANCE，不在多个适配类重复硬编码。
- `simulation`：只接收设备快照、显式命令、模拟步长和稳定身份，产生分配/电量/状态结果；不访问 UI 或现实时间。
- `integration`：读取原版煤炭、人员、落地、模块状态，并应用输出、伤害和原版命令。按实际 1.2.15.3 字节码核对精确入口。
- `state`：电池实例电量、启停、过载请求与损伤余量的版本化数据；明确新造、复制、恢复、断裂、销毁的区别。不能用对象地址或无序容器顺序充当确定性身份。
- `lightning`：确定性目标/能量结算与独立视觉数据；技术保护不能悄悄截断正常攻击预算。
- `client`：图标、按钮、电力条、状态贴图和电弧，仅消费模拟结果；每个负载及每次绘制不重新扫描整船。

第一步先建立上述核心数据与有意义的规则测试，同时核实调度入口、模块身份和保存入口；不要在入口日志类里堆全部逻辑。

## 已核实的框架能力与待验证入口

| 能力 | 现有依据 | 使用边界 |
| --- | --- | --- |
| 原版数据与素材 | Acbric `acbric_vanilla/` 配套资源、`AirshipsDataEvents.DATA_LOADED` | 可随 JAR 管理资源；加载事件可能多次触发，注册需避免重复 |
| 战斗界面 | `AirshipsCombatUiEvents` 状态条/控制面板绘制及输入事件 | UI 回调不能代替战斗模拟 tick；是否足以扩展布局仍需实机检查 |
| 战役数据 | `CampaignData` 版本化 JSON | 不自动同步网络，也不自动覆盖战斗/模块序列化 |
| 电网与战斗行为 | 当前读取的公共 API 未提供可直接使用的电力系统 | 先实现 MOD 内核心及精确适配；不以此任务修改 Acbric 公共接口 |

既有 1.2.15.2 静态研究用于定位候选方法；当前构建输入是 1.2.15.3，不能把前者当成后者的运行验证。重点提前核对一次模拟内供电与模块运行的先后顺序、装填/推力/升力只缩放一次、断裂后的模块身份、独立战斗保存与战役回写。
